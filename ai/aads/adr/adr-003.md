# ADR-003 — AI Runtime Layer

**Status:** Aceita  
**Data:** 2026-08-05  
**Versão:** 0.4.0

---

## Contexto

O AADS 0.3.0 consolidou documentação operacional (workflows, standards, checklists). Agentes ainda precisavam inferir *como executar* o padrão a partir de muitos arquivos. Faltava uma camada de runtime explícita, subordinada ao Operating Model.

## Problema

Como transformar o AADS de framework documental em framework de execução para qualquer LLM, sem reinventar Constitution, SoT, Operating Model ou Completion Model.

## Alternativas

1. Expandir só Cursor Rules — acopla a um host.
2. Duplicar estados do Operating Model em novos docs — viola fonte única.
3. **Criar Runtime Engines subordinados ao Operating Model** — escolhida.

## Decisão

Criar a **AI Runtime Layer** dentro de `engine/`:

| Runtime doc | Papel |
|---|---|
| `execution-engine.md` | Ciclo + checkpoints (mapeia OM) |
| `decision-engine.md` | Árvore de classificação |
| `context-loading.md` | Matriz de contexto mínimo |
| `developer-protection.md` | Zero Trust Developer |
| `validation-engine.md` | Validation Matrix |
| `delivery-engine.md` | Completion State Machine |

Adicionar:

- `standards/compliance-levels.md` — níveis de adoção
- `standards/llm-adapters.md` — packaging multi-host

### Zero Trust Developer

A IA nunca assume memória do desenvolvedor; sempre verifica Issue/Git/Docs/ADR/validações/Completion.

### Multi-LLM

Adapters não criam regras; apenas apontam ao Runtime + Operating Model.

## Consequências

### Positivas

- Comportamento reproduzível entre Cursor/Claude/Copilot/etc.
- Menos ambiguidade de “por onde começar”
- Proteção explícita contra esquecimentos

### Negativas

- Mais arquivos no Engine (mitigado: subordinados, sem copiar OM)
- Necessidade de manter mapeamento Runtime ↔ OM

## Impactos

- SoT: Engine permanece Level 3; LLM Adapters como packaging Level 9
- Entrypoint de execução: Operating Model (canônico) + Execution Engine (orquestração)
- Versão AADS **0.4.0**
